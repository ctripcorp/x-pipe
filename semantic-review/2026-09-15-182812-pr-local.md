# Phase KM Keeper 冷启动、独立 capability 刷新与 DC 异常保留

这轮修复把 Keeper capability 刷新迁到组件自有的单线程 scheduler，在 `DefaultHealthChecker` 中与 Meta manager 按顺序启停，并为 Region 判定增加 fail-closed 过滤。Keeper 冷启动改为逐 cluster 复用 selector，DC 从 Meta 直接消失则保留 manager/instance，仅记录异常。定向测试 33 项全部通过，但文档对 DC 消失的最终语义仍自相矛盾，持续异常会触发周期性高等级日志，新加的销毁与 Region 分支也没有被测试锁定。

Watch for: **confirmed（中）** `spec.md` 同时要求“只日志不下线”和“stop/remove 并清理”；**confirmed（中）** 持续 DC/Region 异常会每轮重复 ERROR，并可能按 Keeper 重复 INFO/WARN；**confirmed（低）** `@PreDestroy` 与 fail-closed 新分支缺少直接测试。

**Verdict**: NEEDS_CHANGES

## High-level view

独立 executor 的启停顺序已接入 `DefaultHealthChecker`，但现有测试只覆盖 mock scheduler 的 cancel 和 manager 调用顺序，没有覆盖真实 Spring 销毁、executor 终止与线程残留。

Region 判定缺失或失败时会跳过 capability 刷新。测试数据始终让 Keeper DC 等于 current DC，因此新增的跨 Region、缺失 Region 和查询失败路径没有执行。

DC 从 Meta 消失后 manager 与实例会持续保留，两个周期任务也会持续观察并记录该异常。与此同时，spec 的 §4.9.1 仍要求清理消失的 DC，与 D42、tasks 和当前实现形成相反合同。

<details><summary>Details</summary>

## DC 消失合同在同一份 spec 中互相冲突

**confirmed（中）** `xpipe-copilot/changes/keeper-tfs-m5/spec.md` 的 D42 规定完整 Meta 快照直接缺少 DC 时只记日志，不 stop/remove manager 或 instance，这与 `tasks.md` 的 T-KM.4、T-KMC.3 及 `DefaultMetaChangeManager.checkDcMetaChange()` 一致。但同一文件 §4.9.1 的“Meta 增量维护”仍写着“manager stop/DC 消失仍按自身 dcId 显式清理”，“冷启动与缺失告警”又要求顶层 stop/remove DC manager。后续 KMC 以该章节作为实现依据，这两个相反合同会直接决定异常时是否拆除在线 Keeper；应统一为 D42/T-KM.4，并注明正常下线必须先移除该 DC 的全部 cluster。

## 保留异常 DC 会放大两个周期任务的日志

**confirmed（中）** `DefaultMetaChangeManager.checkDcMetaChange()` 对每个缺失但保留的 managed DC 每轮记录 ERROR；默认轮询间隔为 `max(2s, 30s)`，且 map 项不会被删除，所以异常持续多久，日志就重复多久。

保留的 TFS Keeper 仍由 `KeeperCapabilityRefreshManager.refreshOnce()` 每分钟扫描。`isInCurrentRegion()` 对跨 Region 逐 Keeper 记录 INFO，对缺失 DC 或 Region 查询失败逐 Keeper 记录 WARN；持续元信息异常因此还可能按 Keeper 数量放大日志。应只在异常出现/恢复的状态转换上记录，或按 DC 限流聚合；周期性 skip 不应逐 Keeper 使用 INFO/WARN。

## 专用 executor 的 Spring 销毁合同没有被测试

**confirmed（低）** `KeeperCapabilityRefreshManagerTest` 全部注入 mock `ScheduledExecutorService`，没有调用 `destroy()`；`DefaultHealthCheckerMockTest.testKeeperManagerLifecycleOrder()` 也只直接调用 `doStart()`/`doStop()`。这些断言不能证明 `@PreDestroy` 会终止自有 executor、销毁后没有 `keeper-capability-refresh` 活线程，或 Spring 依赖方与 capability manager 依次销毁时保持幂等。应增加真实 executor 或最小 Spring context 的销毁测试，并断言 executor 终止和线程不残留。

## 新增 Region fail-closed 分支没有直接断言

**confirmed（低）** `KeeperCapabilityRefreshManagerTest` 中 Keeper 的 `dcId` 与 manager 的 `currentDcId` 都是 `"dc"`，始终走 `isInCurrentRegion()` 的相等快捷路径。现有断言没有覆盖跨 Region、`getCheckInfo()==null`/空 DC、`MetaCache.isCrossRegion()` 抛错，也没有证明这些场景下 `capabilityCache.refresh()` 为零调用。应补齐三类命令零发送断言，防止后续重构退化为 fail-open。
